# Ops Studio — AI 驱动的研发质量治理与容器运维工作台

> 将 UT 治理、MR 检视与合入、质量检查和构建部署组织成可执行、可验证、可追踪的工作流程。

Ops Studio（仓库名 `ops-studio`）面向研发人员、代码检视人员和版本质量负责人，将 Pi Agent 与 CodeHub、WeLink、质量数据源、SSH、Kubernetes 和 Helm 连接起来，覆盖从质量问题发现、测试修复、代码检视到合入跟踪，以及构建、产物对比和环境部署的日常工作。

项目重点解决 AI 进入真实研发流程后的三个问题：**如何把分散操作串成持续推进的任务，如何用测试与远端状态验证执行结果，如何让人工判断和经验进入后续自动化过程。** AI 负责需要理解代码与上下文的修复和检视，平台负责流程编排、结果校验和状态留存，人在关键节点确认质量、处理异常。

## 场景与问题

在多版本、多仓库并行交付中，UT 失败、覆盖率不足、MR 待检视和环境部署往往需要同时推进。相关信息分布在质量报表、代码仓、问题单、群消息和远程环境中，研发人员除了处理问题本身，还需要反复查询状态、传递信息和衔接流程。

| 面向角色 | 典型工作 | 主要痛点 |
| --- | --- | --- |
| 研发人员 | 修复失败 UT、补充测试、提交代码并跟进 MR | 从报表定位到仓库后，仍需准备分支、复现失败、修复、回归、建单和提交；一次修复之后还要持续跟进流水线与检视意见 |
| 代码检视与审核人员 | 接收群内 MR、检查改动、确认意见闭环并审核合入 | MR 链接散落在群消息中；新提交需要复检，旧意见需要核对，流水线、权限和人工结论需要反复确认 |
| 版本与质量负责人 | 汇总多版本质量问题、推进治理、查看成果 | 报告查询、异常筛选和任务跟进分散；难以区分“AI 已执行”“测试已通过”和“代码已合入” |
| 构建与环境维护人员 | 远程构建、比较产物、修改配置、部署和查看资源 | 操作依赖命令与个人经验，涉及不同环境和多个服务；产物差异、配置确认与执行日志缺少统一入口 |

这些工作的共同难点是：单个动作可以脚本化，但跨工具流程仍依赖人工衔接；AI 可以给出建议或修改代码，但实际执行效果还需要工程证据确认。

## 方案与能力

平台以“自动化空间”和“容器运维”承载两类工作，通过工具中心、全局概览和应用中心提供统一入口。自动化概览遵循“先看成果，再处理需要关注的任务”，将已形成的治理成果与待人工处理事项放在同一工作视角中。

| 工作场景 | 当前能力 | 形成的结果 |
| --- | --- | --- |
| UT 治理 | 获取质量报告、筛选待治理仓库，执行基线测试，修复失败用例或补充测试，定向验证与全量回归，关联问题单并创建 MR，跟踪后续流程 | 测试执行证据、修复及新增用例记录、问题单与 MR 关联、治理状态 |
| 群组 MR 检视 | 从配置的 WeLink 群接收 MR，执行 AI 检视与增量复检，读取远端检视意见，检查流水线与门禁，衔接人工审核和 CodeHub 检视、审核、合入 | 当前提交对应的检视结果、意见状态、人工结论、远端合入状态与群回执 |
| 质量检查 | 按版本、团队查询 UT、接口测试和静态检查，筛选异常并导出 CSV | 可追踪的查询任务、异常清单和后续治理输入 |
| 构建与部署 | 环境连接测试与架构探测，单分支构建、双分支构建与产物对比，按服务下载产物，Chart 配置分析、审阅与部署 | 构建产物、文件差异、部署配置、分阶段日志与历史记录 |
| 容器资源管理 | 查询 Kubernetes / Helm 资源，预览和执行支持的资源操作 | 与所选环境关联的资源视图和操作入口 |
| 审核经验复用 | 记录人工审核理由，按仓库整理适用经验，支持编辑、停用和冲突确认，供后续检视使用 | 带来源、适用条件与修订号的服务知识 |

上述场景共享工作台，但各自保留独立的任务与门禁。虚机运维目前为预留入口，应用中心提供外部工具入口管理。

## 核心设计与创新

### 1. 将质量报表转化为可推进的治理任务

UT 治理从报告中的失败用例与覆盖率问题出发，连接仓库准备、基线执行、Agent 修复或补测、测试验证和 MR 流程。平台根据实际测试结果区分失败修复与测试补充，避免只凭历史报表决定当前工作。

修复过程中，将上一轮失败证据交给 Agent 继续处理；提交后，继续跟踪当前提交的流水线与检视状态。流程遇到无法确认的结果时保留任务现场和日志，转为人工处理，让自动化任务具有明确的起点、推进条件和停止条件。

### 2. 用测试证据验证 AI 修复成果

UT 治理要求 Agent 仅修改 `src/test` 下的测试文件，禁止修改生产代码、删除或禁用测试、弱化断言。平台结合文件差异检查、禁止标记检查、测试及断言数量检查，对常见违规改动进行拦截，再执行测试验证；这些检查为质量约束提供支撑，仍需结合代码检视判断测试语义是否合理。

平台解析实际 UT 执行报告，对比基线与回归中的用例标识：

- **修复用例**：基线失败、回归执行通过的用例。
- **新增用例**：基线中不存在、回归执行通过的用例。
- **回归门禁**：命令成功、实际执行了测试、无失败或错误，原有用例未丢失、跳过数未增加，原有成功和失败用例均执行通过。

因此，“生成了测试代码”“测试执行通过”“MR 已创建”和“MR 已合入”分别记录。新增用例数也不等同于覆盖率提升幅度，覆盖率变化仍需通过后续质量报告验证。

### 3. 将群协作转化为提交级的 MR 工作流

平台从日常 WeLink 群协作中接收 MR 链接，在既有沟通方式上增加自动检视、状态跟踪和处理回执。首次检视读取当前 MR 改动；再次提交时，基于上次成功检视的提交进行增量复检，并复核历史意见；无法取得可靠增量时回退全量检视。

检视后通过 CodeHub CLI 重新读取远端意见，以实际未闭环意见决定能否继续。检视结果、人工审核和流水线检查均关联当前提交 SHA；提交变化时，原结果不能直接用于新提交。执行审核、合并等动作时继续检查权限和门禁，并核对远端结果，减少重复操作与状态误判。

### 4. 将人工判断沉淀为可复用的审核经验

标准 MR 检视流程默认启用人工审核，支持记录通过、不通过及原因。列表提供一键审核与批量操作，详情保留完整判断入口；关闭平台人工审核也仍需通过 CodeHub 权限和合并门禁。

人工理由可结合当前改动和历史审核记录整理为仓库级知识，保留来源和适用条件。无冲突的新经验可进入后续检视上下文；与既有知识冲突或需要改写既有结论的内容进入待确认状态，避免自动覆盖已经形成的规则。知识编辑采用修订号校验，并支持停用，使经验复用保留人工修正入口。

### 5. 以确定性流程承接 AI 判断与远程执行

平台将代码理解交给 Agent，将可明确校验的操作交给程序：质量数据按固定规则解析，构建按配置步骤执行，部署从环境与产物信息补全 Chart，在审阅模式下经人工确认后执行，任务状态和日志持续保存。

长任务采用队列与并发限制；构建等流程通过 SSE 展示过程。SQLite 统一保存业务状态，服务重启后对未完成的外部任务标记为需人工处理，不自动重放可能产生副作用的动作。执行结果不确定时先核对状态，让故障处理有可追查的依据。

### 6. 复用平台能力，逐步扩大适用范围

环境配置、任务记录、日志、连接设置和工具入口集中管理，后端按环境、构建、部署、UT、质量检查与 MR 等业务模块组织。新增版本、仓库、团队或环境时，可以复用已有配置与流程；新增业务场景仍需实现对应模块及其门禁。

应用中心支持配置外部 HTTP/HTTPS 工具入口，降低日常入口分散带来的切换成本，也为平台后续扩展保留统一的访问位置。

## 典型工作流变化

| 场景 | 人工处理方式 | Ops Studio 的处理方式 | 人工关注点 |
| --- | --- | --- | --- |
| UT 失败治理 | 查报告、拉代码、复现、修复、回归、建单、提 MR，再逐项跟进 | 报告发现问题后进入治理流程，Agent 按失败证据修复，平台验证并跟踪 MR | 业务断言合理性、复杂异常及最终交付质量 |
| UT 测试补充 | 阅读代码与覆盖率报告，逐个编写和执行测试 | 针对待治理仓库补充测试，定向验证后执行回归，记录实际新增通过用例 | 测试场景有效性与后续覆盖率变化 |
| 群组 MR 协作 | 从群里找链接，逐个检视、查意见、查流水线、找人审核与合入 | 接收 MR 后推进检视与检查，集中呈现人工待办，按权限衔接审核合入 | 业务判断、AI 漏检或误报、异常门禁 |
| 多版本质量检查 | 分别查询版本与检查项，再手工整理异常 | 按版本和团队查询、筛选异常、保存结果并导出 | 异常优先级、责任协调与治理效果 |
| 构建与部署 | 登录远程环境，执行命令、找包、比较文件、修改配置并部署 | 统一管理任务、产物与差异，按服务确认配置并执行部署 | 环境选择、配置差异和部署结果 |

## 项目价值与成效衡量

### 业务价值

- **减少流程衔接成本**：将报告查询、测试执行、MR 跟踪和群回执连接起来，减少重复查询、信息搬运与人工盯守。
- **提升质量过程的可检查性**：用基线与回归报告核验测试成果，以当前提交的远端意见、流水线和门禁状态约束 MR 推进。
- **缩短协作反馈路径**：将分散的待审核、待修复和异常任务集中呈现，使人员更快定位需要判断的事项。
- **积累可复用的工程经验**：将人工审核理由转化为带来源和适用条件的服务知识，供后续检视参考和修正。
- **支持持续推广**：以配置和模块化能力复用多版本、多仓库、多环境的治理与运维流程，逐步扩大自动化覆盖范围。

适用于多仓库、多版本并行研发中的 Java / JavaScript UT 治理、团队 MR 协作、版本质量检查和 Kubernetes 环境构建部署。

### 已具备的成效记录能力

| 衡量方向 | 可使用的记录或指标 | 解释边界 |
| --- | --- | --- |
| UT 治理产出 | 修复用例数、新增通过用例数、修复及补测服务数 | 来自基线与回归结果对比；不能直接等同于已合入成果或覆盖率提升 |
| MR 交付情况 | 处理 MR、已合入 MR、待处理与异常记录 | 按仓库和 MR 标识去重，区分重复检视次数与 MR 数量 |
| 人工协作成本 | 人工介入次数、审核次数、审核等待中位数与 P90 | 等待时长体现流程延迟，不能直接视为人工投入工时 |
| 检视质量反馈 | 人工标记的 AI 漏检、误报、不通过原因 | 反映已记录的反馈；未经完整样本核验不能称为检视准确率 |
| 知识复用 | 有效知识条数、知识使用记录 | 使用次数体现引用情况，不代表已证明的质量收益 |
| 构建部署过程 | 执行状态、阶段日志、产物与差异记录 | 任务完成时长与人工操作时长应分开统计 |

## 技术实现与使用说明

前端采用 Vue / Vite，后端采用 TypeScript / Fastify，业务状态存储于 SQLite。资源中心、SSH 连接、远程构建、容器资源、部署、Auto-UT/Agent 和持久化任务均由一个 Node.js 进程提供；平台后端不依赖 Java、Maven 或 Spring Boot，Java UT 治理仍需目标项目要求的 JDK / Maven 环境；JS UT 治理需要 Node.js / npm 及项目依赖仓库访问权限。

不同能力按需准备 Pi Agent、CodeHub CLI、WeLink CLI / MCP、质量数据源及远程环境访问条件。相关身份认证和操作权限由对应工具与目标系统校验。

## 启动

需要 Node.js 24.15+（24.x）和 npm。Windows 双击 `start.bat`，脚本会按锁文件安装依赖、迁移检测到的旧 H2 数据、编译后端，然后启动：

- TypeScript 后端：`http://127.0.0.1:8080`
- Vite 前端：`http://127.0.0.1:5173`

手动启动：

```bash
npm ci
npm run migrate
npm run build
npm start
```

另开终端启动前端：

```bash
npm ci --prefix frontend
npm run dev --prefix frontend -- --host 127.0.0.1
```

## 页面入口

首页为工具中心（`#/home/tools`），全局概览（`#/home/overview`）只汇总已保存的任务和环境状态。自动化、容器运维的原有页面地址继续可用；虚机运维保持预留状态。

应用中心（`#/applications`）可创建、编辑和删除 HTTP/HTTPS 工具入口，填写地址、功能说明并关联工作空间。应用配置保存在现有 SQLite 中，全平台共享；收藏仅保存在当前浏览器。站内打开使用 iframe，目标网站不允许嵌入时可选择新标签页打开。后端不会代理访问目标网站，也不增加账号或权限体系。

部署页的“历史任务”可查看任务并单条或批量删除。仅允许删除已成功或已失败且执行已结束的记录；删除不会卸载 Helm、修改集群资源或删除构建产物。批量操作逐条确认结果，失败不会自动重试。

## 结构

- `backend-ts/src/modules/environment`：环境配置和 SSH 连接测试
- `backend-ts/src/modules/build`：远程构建、产物与可重放 SSE
- `backend-ts/src/modules/containerresource`：Kubernetes/Helm 资源发现、预览和变更
- `backend-ts/src/modules/deployment`：Chart 补全、审阅、渲染和串行部署
- `backend-ts/src/modules/autout`：CSV 扫描、Agent 修复、测试门禁和 CodeHub MR
- `backend-ts/src/modules/automation`：群组 MR 检视、人工审核、服务知识、执行记录与成效统计
- `backend-ts/src/modules/quality`：UT、接口测试与静态检查查询、异常筛选和 CSV 导出
- `backend-ts/src/modules/applications`：应用中心外部工具入口
- `backend-ts/src/platform`：SQLite、独立 Worker和通用只读任务
- `shared`：前后端共享的数据约定
- `frontend` 与根目录 `index.html`：现有 Vue/Vite 页面

SQLite 默认写入 `data/platform/tasks.sqlite`。数据库使用进程独占锁，不能同时启动两个后端。服务只允许本机浏览器来源；它没有多用户认证，不能直接暴露到公网。

## 日志

运行日志统一写入项目根目录的 `data/logs`，同时继续显示在启动窗口和页面中。每次运行 `start.bat` 都会先清空该目录，确保导出的日志只包含本次运行：

- `startup/startup.log`：依赖安装、数据迁移和编译
- `backend/process.log`：Node.js 后端进程启动输出
- `backend/backend.jsonl`：Fastify 请求与服务异常，JSON Lines 格式
- `frontend/frontend.log`：Vite 前端进程输出
- `platform/{taskId}.jsonl`：通用平台任务事件
- `build/{taskId}.jsonl`：构建步骤和远程命令输出
- `deployment/{taskId}.jsonl`：分析、编辑、渲染和部署输出
- `automation/group-mr-monitor.jsonl`：群组 MR 监听轮询、过滤数量、命令状态和错误（不记录群消息正文）；页面“群组 MR 检视 → 监听日志”展示最近 100 条
- `auto-ut/{taskId}.jsonl`：Auto-UT 阶段与实时事件
- `auto-ut/details/{taskId}/*.log`：Git、Maven、npm/Jest、Agent 和 CodeHub 命令的完整输出

JSON 日志会按敏感字段名脱敏。诊断时优先发送对应任务 ID 的日志文件，不要发送包含环境密码的 `data/platform/tasks.sqlite`。

旧 H2 数据迁移由 `scripts/migrate-legacy-h2.mjs` 提供；构建、部署和 Auto-UT 的实际执行约束以对应模块的校验逻辑为准。

## 验证

```bash
npm run check
npm run test --prefix frontend
npm run typecheck --prefix frontend
npm run build --prefix frontend
```

SSH 用户名仍按环境类型固定：构建环境使用 `huawei`，容器环境连接测试使用 `sopuser`，Kubernetes/Helm 操作使用 `root`。密码不会写入应用日志。

构建产物下载和双分支文件对比要求远端构建环境提供 `python3`（仅使用标准库）。服务目录按需打包；已有 `.tgz` / `.tar.gz` 包原样下载。批量下载返回包含各服务包的 `.tar.gz`；包内链接或越界路径会拒绝处理。对比结果保存在 SQLite，文本差异有大小限制，截断或二进制文件会提示下载原包查看。

### JavaScript UT 治理

JS / JavaScript 报告可独立启动治理；同仓库的 Java、JS 使用独立任务和修复分支，工作目录统一为 `<工作根目录>/<版本>/<仓库名>`，同一目录需依次治理。升级前已创建的 JS 任务继续使用其原目录，避免丢失修复现场；新任务不再创建 `.auto-ut-js` 层级。Python 等其他语言显示暂不支持自动修复。

克隆后必须已有 `website/package.json`，且 `scripts.test` 使用已支持的 Jest 执行入口（直接调用、npm 脚本别名，或 react-scripts / react-app-rewired test）。其他测试框架需接入相应结果解析，不能直接套用 Jest 参数。平台在 `website` 内依次执行：

```sh
npm install --force --ignore-engines
npm run test -- --watch=false --watchAll=false --ci --runInBand --json --outputFile=<任务日志目录>/jest-results.json
```

安装期间产生的 package.json / 锁文件变更会恢复；依赖目录留在工作区供后续验证使用。基线、修复验证、完整回归和 MR 流水线修复均读取本轮 Jest 报告；依赖缺失、套件加载失败、无有效用例和超时会阻断，不当作可修复的用例失败。缺少 website 初始化文件时明确报错，不自动执行 Maven。

仅允许提交 website 中的测试与 mock 文件，支持 `.test.js`、`.test.jsx`、`.spec.js`、`__tests__` 等测试路径；禁止修改生产源码、配置、锁文件和已有快照。原用例必须保留并通过，不能靠跳过测试达成成功。覆盖率仍以质量报告为准。

### UT 问题排查日志

日志默认位于 `data/logs/auto-ut/details/<任务ID>/`，设置 `PLATFORM_LOG_DIR` 时以该目录替代 `data/logs`。Java / JS 共用命令诊断：

- `diagnostics.jsonl`：任务、语言、阶段、轮次、工作目录、命令参数、开始/结束时间、耗时、退出码、超时/中断、日志文件名；JS 另记报告解析结果与阻断原因。
- `<操作名称>-<唯一ID>.log`：每次 Git、npm、Maven、Agent 命令的完整逐行输出，带时间及 stdout/stderr 来源；重试不会覆盖上一轮，文件不受内存输出摘要长度限制。
- `jest-results-<唯一ID>.json`：每轮 Jest 报告独立留档，包括测试数量、具体失败用例及堆栈。当前轮报告缺失或无法归档会记录原因状态。

日志会遮蔽常见凭据字段、认证头、URL 密码及环境中的密钥值，不记录完整环境变量或命令标准输入。遇到问题请提供任务 ID 和对应任务日志目录。主动删除任务并清理目录会一并删除该任务详细日志，请先留存；MR 合入后的自动仓库清理保留日志。
