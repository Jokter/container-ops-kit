# 代码检视意见模板

遵循调用方要求的输出格式。行内检视默认用简短自然段，不必展开为分类报告；无需填写所有检查项，没有发现问题时不凑意见。

## 单条意见

定位到最能体现根因的文件和代码行，正文按以下顺序自然表达：

> [观察到的代码现象]。[触发条件与可能影响]。请确认[未知的业务限制或保护措施]，是否需要[可选的改进方向]？

已证实缺陷直接说明，不刻意改成疑问；疑点不得把未知条件当作事实。优先级根据影响判断，不能靠标签替代实际门禁。

### 大 SQL

> 这里按租户读取全部历史任务后在内存筛选，调用链未看到数量限制。历史任务增长时可能返回较多数据，请确认任务量是否有上限，是否需要将筛选下推并分批读取。

### 大规格

> 这里为列表中的全部资源同时发起详情请求，未看到并发限制。资源较多时可能集中占用连接，请确认最大规格下的数量及调用层是否已有统一限流。

### 设计维护

> 同一类型判断在创建、更新和校验流程中重复，增加类型需同步修改多处，可能遗漏。是否考虑集中维护类型处理逻辑？若这些流程会独立演进，也可以保留当前结构并说明原因。

## 复核已有意见

- 引用原意见 ID，结合当前代码和开发回复说明结果，不重复创建。
- 区分代码修复、业务解释、接受风险和仍未处理；“收到”“稍后处理”不代表问题已解决。
- 解释使疑点不成立时说明依据和待确认内容，不强制要求改代码；关闭或接受风险遵循调用方的人工确认流程。
- 无法判断时直接说明缺少的上下文，不伪造确认结果。

## 最终简述

简要说明实际检视范围、旧意见复核结果与新增意见数量。若调用方要求结构化结果，严格使用其格式；不要自行执行审核、通过或合入。
