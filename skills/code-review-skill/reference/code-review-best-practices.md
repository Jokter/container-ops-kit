# 代码检视最佳实践

开展有效代码检视的完整指南。

## 检视理念

### 代码检视的目标

**主要目标：**
- 在上线前发现缺陷和边界情况
- 确保代码可维护、可读
- 在团队内分享知识
- 一致地落实编码规范
- 改进设计和架构决策

**次要目标：**
- 指导初级开发人员
- 建立团队文化和信任
- 通过讨论记录设计决策

### 代码检视不应成为

- 阻碍进度的把关机制
- 炫耀知识的机会
- 纠缠格式细节的场所；此类问题使用静态检查工具处理
- 根据个人偏好重写代码的方式

## 检视时机

### 何时开展检视

| 触发条件 | 行动 |
|---------|--------|
| 新建合并请求 | 24 小时内检视，最好当天完成 |
| 请求修改 | 4 小时内重新检视 |
| 发现阻塞问题 | 立即沟通 |

### 时间分配

- **小型变更（少于 100 行）**：10～15 分钟
- **中型变更（100～400 行）**：20～40 分钟
- **大型变更（超过 400 行）**：建议拆分，或安排 60 分钟以上

## 检视深度

### 第一级：快速浏览（5 分钟）
- 检查合并请求描述和关联问题
- 确认 CI/CD 状态
- 浏览文件变更概况
- 判断是否需要深入检视

### 第二级：标准检视（20～30 分钟）
- 完整走读代码
- 验证逻辑
- 检查测试覆盖
- 安全扫描

### 第三级：深入检视（60 分钟以上）
- 架构评估
- 性能分析
- 安全审计
- 探查边界情况

## 沟通指南

### 语气和表达

**采用协作式表达：**
- 使用“你怎么看……”，避免“你应该……”
- 使用“是否可以考虑……”，避免“这不对”
- 使用“我想了解……”，避免“你为什么不……”

**反馈应具体且可执行：**
- 提出修改建议时给出代码示例
- 附上文档或历史讨论链接
- 解释建议背后的原因

### 处理分歧

1. **先理解对方**：通过问题澄清意图
2. **认可合理之处**：表明已考虑对方的观点
3. **提供依据**：使用基准测试、文档或示例
4. **必要时升级讨论**：邀请资深开发人员或架构师参与
5. **适时停止争论**：并非每个细节都值得坚持到底

## 检视优先级

### 必须修复（阻塞合入）
- 安全漏洞
- 数据损坏风险
- 没有迁移方案的不兼容变更
- 严重性能问题
- 面向用户的功能缺少异常处理

### 应当修复（重要问题）
- 测试覆盖缺口
- 中等程度的性能隐患
- 重复代码
- 命名或结构不清晰
- 复杂逻辑缺少文档

### 可选改进（不阻塞合入）
- 静态检查规则之外的风格偏好
- 小幅性能优化
- 补充测试用例
- 改进文档

## 应避免的反模式

### 检视者反模式
- **走过场审批**：没有真正检视就批准
- **纠缠琐事**：花大量时间争论无关紧要的细节
- **范围蔓延**：“既然改了这里，能否顺便再……”
- **提出要求后失联**：要求修改后不再跟进
- **过度追求完美**：因为轻微的风格偏好阻塞合入

### 代码作者反模式
- **超大变更**：一次提交超过 1000 行的修改
- **缺少上下文**：没有合并请求描述或关联问题
- **防御性回应**：对每一条建议都争辩
- **静默更新**：修改了代码却不回复检视意见

## 指标与改进

### 跟踪以下指标
- 首次检视等待时间
- 检视周期
- 检视轮次
- 缺陷逃逸率
- 检视覆盖率

### 持续改进
- 定期复盘检视流程
- 分享逃逸缺陷带来的经验
- 根据常见问题更新清单
- 肯定高质量检视和有效的问题发现
